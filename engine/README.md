# lefdata — 주행 데이터 분석 엔진

대학 포뮬러 동아리 **라이트온(LightOn)** 차량(LEF-25evo · LEF-26 → LEF-27)의 로거 데이터를 읽어,
장비가 달라도 같은 모양의 표로 바꾸고(정규화), 장비끼리 시계를 맞추고, 랩 · 구간을 나누고, 데이터 뷰어 사이트가 부를 함수를 낸다.

- **원본은 고치지 않는다 · 모르는 값은 추측으로 채우지 않는다 · 깨진 데이터는 지우지 않고 `valid` 로 표시한다**
- 계산은 전부 여기서 한다. 사이트(이 저장소의 다른 폴더)는 받은 값을 보여 주기만 한다
- 주행 데이터는 이 저장소에 없다. 데이터 폴더는 `LEF_DATA_ROOT` 로 지정한다 (없으면 데이터가 필요한 테스트 · 명령은 건너뛰거나 멈춘다)

## 읽는 장비

| 소스 | 차량 | 하는 일 |
|---|---|---|
| Monolith V2 바이너리 `.log` | LEF-25evo | 레코드 해독(GPS · IMU · 아날로그 · 이벤트), 체크섬 |
| LEF-26 자작 로거 CSV | LEF-26 | CAN(BMS · 모터 컨트롤러 · 써미스터 모듈) · IMU · 지자기 · 리니어 센서 해독, 로거 시계 보정 |
| FSK 에너지미터(FSK-EEM) `.log` | 공통 (대회 주최측 장비) | 공개 펌웨어 형식대로 전압 · 전류 · LV 전압 · 장치 온도 · 체크섬 |
| 25Evo STM32 백업 로거 CSV | LEF-25evo | BMS · 모터 값, 잘린 바이트 되살리기, 시계 속도 보정, 다른 장비에 시간 맞추기 |
| GoPro 온보드 영상 (GPMF) | 공통 | 영상을 풀지 않고 GPS · 가속도 · 자이로만 꺼내기, 표본 시각 복원 |
| Orion BMS Connect (Utility 변환 CSV) | LEF-25evo | 셀 · 팩 · 제한 상태 |

## 설치

```bash
cd engine
python -m venv .venv
.venv/Scripts/python -m pip install -e ".[dev]"     # Windows (리눅스 · 맥은 .venv/bin/python)
```

## 명령

```bash
lefdata monolith | lef26 | energymeter | evo-stm32 | orion | gopro --event <이벤트>   # 장비별 원본 → normalized/
lefdata laps --event <이벤트>          # GPS 로 주행 구간 · 랩 → derived/ (gopro 는 --laps)
lefdata events --event <이벤트>        # 가속(75 m) · 스키드패드
lefdata motor-runs                    # GPS 없는 로거: 모터 속도로 주행 구간
lefdata em-laps --event <이벤트>       # 에너지미터를 GPS 랩에 붙이기 (전력 ↔ 위치로 시계를 맞춘다)
lefdata lef26-clock | lef26-laps      # LEF-26: 로거 시계 검증 · 랩마다 로거 값
lefdata clocks                        # 장비끼리 시계 차 · 전원 주기로 짝짓기
lefdata check --event <이벤트>         # 데이터 품질 검사
lefdata report --day <날짜> --pdf      # 하루치 시험 주행 보고서 (HTML · PDF)
lefdata sessions                      # 분석 엔진(lefdata.api)이 읽는 세션 저장소
pytest                                # 테스트 (아래 §테스트)
```

## 출력 — 공통 포맷

```
<이벤트>/normalized/
├─ recordings.csv          레코딩 목록 (레코딩 = 장비 전원 1회, 영상은 녹화 1회)
└─ <recording_id>/
    ├─ meta.json           출처 · 시간 기준 · 품질 지표 · 변환 성능
    ├─ frames.parquet      원본 레코드 전부 (해석 전, 보관용)
    └─ <신호>.parquet      gps · imu · bms · motor · energy · thermistor · lin · mag …
<이벤트>/derived/          해석 결과 (주행 구간 · 랩 · 시계 맞춤 · 그림)
```

모든 표의 공통 시간 열: `t_rel_ms`(레코딩 시작 기준 ms) · `t_abs`(절대 시각, 모르면 null) · `t_quality`(그 시각을 어떻게 얻었나).

| `t_quality` | 뜻 |
|---|---|
| `boot_rtc` · `meter_rtc` | 장비 내부 시계 |
| `synced` · `continuity` | GPS 로 맞춘 뒤 / 맞추기 전 구간을 이어 붙여 역보정 |
| `aligned_em` · `aligned_gps` | 다른 장비의 파형에 맞춰 찾은 시각 |
| `gps_utc` · `gps_utc_uncal` | 영상 GPS 시각 / 가속도계 시각을 GPS 에 못 맞춘 조각 |
| `none` | 기준이 없어 절대 시각 없음 |

- 로거 시계가 느리게 가는 장비는 변환기가 경과 시간을 바로잡아 `t_rel_ms` 에 쓰고, 로거가 찍은 그대로는 `frames.t_log_ms` 에 남긴다
- ⚠ **IMU 축 이름이 차량 축과 다를 수 있다** (칩 축 그대로 기록한 로거). 이 엔진은 물리적 뜻으로 이름을 붙이거나(LEF-26: `ax_lat_g` · `ay_long_g`) 원래 이름을 두고 문서에 적는다.
  부호는 GPS 로 한 번 더 확인한다

## 품질 검사 (`lefdata check`)

"이 데이터 믿어도 되나" 에 답한다. 판정이 아니라 **측정값과 함께** 돌려주고, 기준은 전부 인자로 받는다.

| 검사 | 잡는 것 |
|---|---|
| 물리 범위 | 체크섬은 통과했는데 말이 안 되는 값 (다른 장치의 프레임이 섞인 경우 등) |
| 전 구간 같은 값 | 꽂히지 않은 센서 |
| 시각 단조성 · 레코딩 겹침 | 시계가 되감긴 기록, 같은 장비가 같은 시각에 두 번 |
| 기록 공백 · 중복 행 · 행 수 보존 | 빠진 구간, 같은 줄이 여러 번, 변환하며 사라진 행 |
| 중력 크기 · 독립 측정 대조 | IMU 배율 오차 (정지 구간에서만 판정 — 주행 중에는 1 g 를 넘는 게 정상) |

검사 도구도 틀린다 — 그래서 검사 함수 자체도 만들어 낸 값으로 테스트한다.

## 계층 — 떼어낼 수 있게

| 계층 | 모듈 | 성격 |
|---|---|---|
| **공개 계층** | `laps` `events` `gopro` `quality` `sync` `series` | 차량 · 폴더 구조를 모른다. FSAE 규격(75 m 가속, 스키드패드)은 공통이라 다른 팀 데이터에도 그대로 쓴다 |
| 팀 계층 | 장비 어댑터, 폴더 구조, 차량 상수, 보고서 · 엔진(`api`) | 우리 로거 · 폴더를 안다 |

방향은 한쪽뿐이다 — 팀 → 공개는 되지만 반대는 안 된다 (`tests/test_layering.py` 가 감시한다).
덕분에 로거 GPS 가 없던 차의 랩을 온보드 영상 GPS 로 셀 수 있었다 — `laps.py` 는 GoPro 를 모르지만 같은 모양의 표를 받았다.

## 랩 · 종목

- **랩 분할** — 속도로 주행 구간을 나누고, 빠르면서 주변에 다른 트랙 구간이 없는 지점에 계측선을 자동으로 긋는다. 한 이벤트의 레코딩은 전부 같은 계측선 · 같은 좌표 원점을 쓴다
  (→ 같은 이벤트의 세션끼리 랩을 겹칠 수 있다). 계측선 폭은 GPS 위치가 밀려도 통과를 놓치지 않을 만큼 넓게
- **가속 75 m** — 주행 구간 시작은 이미 속도가 붙은 뒤라, 거슬러 올라가 정지했던 마지막 지점을 출발로 잡는다 (안 그러면 기록이 빨라진다). 위치 적분 · 속도 적분 두 가지로 재서 대조
- **스키드패드** — 8자 전체를 원 하나로 맞추지 않는다. 진행 방위 변화율의 부호로 좌 · 우 호를 먼저 나눈 뒤 각각 원을 맞추고, 중심 기준 360° 를 채운 호만 센다.
  원에 잘 안 맞는 호(원을 빠져나가는 구간)는 세지 않는다. ⚠ 진행 방위는 시계 방향이 증가라 양수가 우회전이다
- 서로 다른 GPS(주기가 다른 수신기)끼리는 출발 순간 판정이 달라질 수 있어, 0.1 s 단위의 차량 간 비교에는 쓰지 않는다

## 장비끼리 시계 맞추기

같은 물리량(요레이트 · 속도 · 전압 · 전력)을 잰 두 장비라면 파형으로 시계 관계를 구한다 (`sync`).

```python
k_ref, ref = sync.grid(t_ref, yaw_ref)            # 고른 격자
k_sig, sig = sync.grid(t_sig, yaw_sig)
m = sync.match_windows(k_ref, ref, k_sig, sig)    # 창마다 가장 닮은 위치
fit = sync.fit_clock(m["ref_s"], m["sig_s"])      # sig 시각 = a + f × ref 시각.  f = 시계 속도
```

- **어긋남(초)만 찾으면 틀린다.** 시계 속도가 다르면 긴 기록의 어느 한 지점도 맞지 않는다 — 어긋남과 속도를 같이 구한다. 맞추기 전에 두 기록의 길이가 같은지부터 본다
- 같은 코스를 도는 랩끼리는 파형이 닮아 틀린 짝이 섞인다. `fit_clock` 은 한 직선에 가장 많은 점이 모이는 기울기를 고른다
- 절댓값(예: 전압 수준)은 **어느 구간인지**, 창 맞춤은 **정확히 언제 · 얼마나 빠르게** 에 쓴다. 상관만으로 고르면 평평한 파형끼리 엉뚱하게 붙는다
- **에너지미터 ↔ GPS** (`em_laps`): 같이 잰 물리량은 없지만 전력 P = V·I 와 "차를 미는 일률 (가속 + 주행저항) × 속도" 는 같은 모양이다. 일률은 위치에서 낸 속도로 만든다
  (랩을 위치로 끊으므로). 맞춘 뒤 랩 · 구간마다 에너지를 **시간으로 적분**한다 (빠진 표본이 있어도 맞게)
- **전원 주기로 짝짓기** (`clocks`): 같은 전원 스위치에 물린 장비들은 같이 켜지고 꺼진다 — 파형 없이도 짝을 짓고 시계 차를 바로 구한다
- 구간마다 **붙인 것을 믿을 근거**를 같이 적는다: 덮은 비율, 그 구간만 따로 다시 대 본 어긋남과 상관. 덮지 못한 구간은 값을 비운다

## 온보드 영상 (GoPro GPMF)

- 영상을 풀지 않고 텔레메트리 기록만 읽는다. 카메라 시계는 쓰지 않고 레코딩 이름 · 시각은 GPS 에서 온다. 4 GB 마다 쪼개진 파일은 한 레코딩으로 잇는다
- GoPro 는 표본마다 시각을 주지 않는다 — 블록 시각과 다음 블록까지의 간격으로 표본 시각을 나누고, 자이로는 가속도 시각에 맞춰 평균 · 보간한다
- **같은 블록에 든 IMU 와 GPS 는 같은 순간이 아니다.** IMU 가 정수 초만큼 늦게 들어 있고 파일마다 다르다 — GPS 궤적이 휘는 속도와 자이로를 겹쳐 재고 당긴다. 잴 수 없는 조각은 `gps_utc_uncal`
- GPS 속도 열은 같은 GPS 의 위치보다 조금 늦게 나온다 — 다른 장비의 시계를 영상에 맞출 때는 위치에서 낸 속도를 쓴다
- 카메라 가속도는 서 있을 때의 중력 방향을 '위' 로 삼아 차량 축으로 바꾸고, 세션마다 GPS 에서 낸 가속도 · 요레이트와 대조한다

## 분석 엔진 — 데이터 뷰어 사이트가 부르는 함수 (`lefdata.api`)

```python
from lefdata import api
api.list_sessions()                                   # 세션 목록 (최신순, limit · offset)
api.get_session(sid)                                  # 요약 · 데이터 현황 · 블록(사실 · 확인 · 주의 · 원본 · 코드) · 없는 데이터
api.list_channels(sid)                                # 채널: 단위 · 부호 · 주기 · 장비 · 계산한 값인지 · 주의
api.get_series(sid, ["battery.current_a", "imu.long_g"], max_points=4000)   # 같은 x 위의 평균 · 최소 · 최대
api.get_series(sid, ["gps.speed_kmh"], x="distance", lap=7)                  # 랩마다 계측선부터의 거리축
api.get_laps(sid) · api.get_track(sid, color="battery.power_kw") · api.get_quality(sid) · api.open_file(file_id)
```

| 모듈 | 하는 일 |
|---|---|
| `api` | 사이트가 부르는 함수. 돌려주는 값은 전부 JSON 으로 바꿀 수 있고, 없는 값은 `None`. 잘못 부르면 `EngineError` (`.to_json()`) |
| `session_store` | 세션을 저장소로 미리 만든다 (요약 · 원래 주기 채널 값 · 랩 · 궤적 · 품질 경고 · 내려받을 파일 표). 부를 때마다 원본을 다시 읽지 않게 |
| `series` | 그래프 값 줄이기 — 칸마다 평균 · 최소 · 최대를 같이 줘서 줄여도 순간 피크가 남는다. 빈 칸은 양옆이 끊기지 않았을 때만 직선으로 잇는다 (기록 간격의 2 배 넘게 빈 곳은 비운다) |

- 세션을 채우는 것은 `catalog_build.build_event` (차량 · 폴더를 아는 코드는 거기 한 곳). LEF-27 은 `Session` 을 채우는 함수만 새로 쓰면 된다
- 드라이버는 `드라이버 A` 같은 표시만 저장소에 들어간다 (그 밖의 글자는 거절한다)
- 함수 이름 · 인자 · 돌려주는 모양은 사이트와의 계약이다. 바꿀 때는 계약 문서를 먼저 고치고 `api.CONTRACT_VERSION` 을 같이 올린다

## 시험 주행 보고서 (`lefdata report`)

하루치 시험 주행을 문서 한 장(HTML, `--pdf` 로 A4 PDF)으로 만든다 — 요약 · 시험 개요 · 랩 기록 · 차량 거동 · 배터리 · 구동계 · 데이터 품질 · 조치 사항.

- **수치는 데이터에서, 판단은 사람이.** 시험 목적 · 세팅 · 판단 · 조치는 `<이벤트>/report_notes/<날짜>.toml` 에 적는다. 없으면 "기록 없음" 으로 나온다 — 지어내지 않는다
- 문서 · 그림 코드(`report` · `report_charts`)는 차량을 모른다. 차량마다 `DayReport` 를 채우는 함수 하나만 쓰면 같은 보고서가 나온다
- 그림 안에는 데이터 · 단위 · 시각만, 해석은 본문에. 글자는 Pretendard (`assets/fonts/`, SIL OFL)

## 테스트 — 보편 테스트와 기대값 파일

| | 무엇 | 숫자는 어디에 | 데이터 없이 |
|---|---|---|---|
| 보편 테스트 | 만들어 낸 데이터의 단위 테스트 + 형식 · 물리에서 늘 참인 불변식 (시간 단조, 체크섬, 방위 0 ~ 360, 에너지 = 전력의 적분, 빈 값을 0 으로 채우지 않음 …) | 코드 (단위 · 물리 상수 · 형식의 정의 · 방법의 허용 오차만) | 돈다 |
| 골든 테스트 | 실제 데이터에서 나온 값 — 개수 · 시각 · 길이 · 측정값 · 레코딩 이름 · 차/코스에 묶인 범위 | **기대값 파일** `<데이터 폴더>/_expected/<이름>.toml` (값 + 그 이유). 코드는 "파일의 값과 맞는가" 만 본다 | 건너뛴다 |

- 쓰는 법은 `tests/expected.py` 맨 위, 예시는 `tests/expected_example/example.toml` (합성 세션의 값)
- 끝에 "기대값 파일에서 쓰지 않은 값" 이 나오면 그 값을 보던 검사가 빠진 것이다
